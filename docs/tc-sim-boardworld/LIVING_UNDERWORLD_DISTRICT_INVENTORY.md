## Proposed minimum district authority (not implemented)

This contract is a proposed integration boundary, coordinated with the simulation workstream; final phase-2 IDs, bounds, schema and ownership still require integration review after recovery. One source owns each fact and every write occurs in `resolveAction` or deterministic day/month hooks on the cloned state. Views and forecasts are pure and cannot charge, tick, reveal undiscovered evidence or consume RNG.

### Identity, compatibility and projection

- Preserve Gold `s.location` and `s.city.venue` and their existing IDs for İstanbul. Preserve expansion `s.expansion.world.region` as the city authority. A **read-only** place adapter returns `place = { regionId, districtId, venueId }`: in İstanbul it projects the existing Gold IDs; elsewhere it projects an explicitly chosen expansion district/venue, or `null` when no local selection exists. It must never reinterpret a stale İstanbul `s.location` as a district in Ankara/İzmir or silently relocate an NPC.
- New regional district and venue IDs are city-qualified, e.g. `ankara:<authored-id>` and `<district-id>:<venue-id>`; reserve the names only after an authored mapping is approved. Do not rename or reuse the existing `<region>:<home>` property IDs. A migration/normalizer must distinguish old Gold IDs, existing lot IDs and new district IDs; invalid references fail validation or surface recovery, not a fallback teleport.
- Expansion state may hold bounded per-region district/venue selections and only the additional local deltas not owned elsewhere. A legacy save opens unchanged: derive defaults in memory without rewriting saved bytes; initialize/normalize optional state on the first authorized real mutation. Never enable expansion merely to view its preview. Persist through the existing generation lock, schema validation, export/import, rollback and successor pipeline; introduce any schema change only with explicit integration review.
- `getDistrictSimulation(state, districtId)` is an **internal** pure projection for resolver/tick eligibility and pricing: `{ demand, rentPressure, foodStock, materialStock, jobOpenings, serviceDelay, security, influence }` with documented units/bounds. It references existing markets, society, property and faction authority; it is not an independent money/stock ledger. `getDistrictView(state, districtId)` exposes only public/player-known facts and available IDs, including actual costs, time, conditions and causal explanations. No UI code reads undiscovered evidence, other actors' hidden balances or internal rolls.

### Catalog and capabilities

A catalog record needs stable `{ id, regionId, displayKey, kind, connections, capabilities }`; a venue needs `{ id, districtId, kind, opening, capacity, actionIds }` with actual hours/availability. Labels are TR/EN/PL presentation data, never identity. At minimum each activated district must connect to:

1. **Housing**: a real lease/owned lot and due dates, one authoritative rent/mortgage/maintenance settlement, with a regional-lot link rather than cloning existing lot assets.
2. **Work and trade**: an employer or real job opening, a business/service using finite stock, worker and customer capacity, real funds and a locality modifier; no synthetic wage or duplicated inventory.
3. **Public institution**: school, clinic, credit or council capability backed by the existing institution region state, fee, time and consequences; location changes access, not the ownership of the credit/case/treasury.
4. **Social venue**: an open, reachable meeting or community place tied to NPC presence and the canonical calendar. Closing hours, travel and appointment conflict checks must be shared by preview and resolver.
5. **Transport**: route edges `{ from, to, mode, minutes, cost, availability }` and intercity transition. A route affects time, cash and energy once; return-home, calendar and NPC location semantics must agree. Locality is an actual action precondition, not a decorative map marker.

Do not label a district functional until all applicable capabilities resolve to real available or reasoned-unavailable actions. Initial coverage can be deliberately small and explicit rather than asserting that all 23 reference records are simulated.

### Faction/economy interface agreed in principle with Sol

A future expansion-owned `underworld` namespace may contain keyed `chapters`, `memberships`, `evidence`, and `cases`; `membership` singular is only a public projection for the current character. A chapter has a stable ID and district link, finite treasury/stock, standing and bounded influence; a membership has person/chapter IDs, status, trust, responsibility and rank, plus dated transitions. These are proposed fields, not a claim they already exist. Store only values not already held in the enterprise, household, institution or society ledgers. Pass read-only district modifiers into those authorities and use their existing transactions through explicitly reviewed hooks. Do not debit both a chapter treasury and player/enterprise account for the same cost or create a second tenancy.

`underworld:*` actions must have stable disjoint IDs, deterministic ordering, minutes, cost payer, eligibility and visible reason/forecast. The resolver checks location, hours, available funds/stock/capacity, actor status and conflicts immediately before one atomic mutation. A missed or invalid action commits no partial transfer. If an event can affect travel, a job, an invitation or service, it uses the existing clock/calendar and action authority; city, organization and evidence systems must not run independent wall clocks or competing ticks.

## Six loops: minimal causal acceptance

| Loop | Minimum authoritative action chain and visible result |
| --- | --- |
| Legal life | Travel to a real opening → apply/shift → employer funds wages once → household budget pays rent or buys a real property → advancement follows actual work/qualification. Show requirement, payer, duration, effect, rent/debt and next due time. |
| Organization | At a reachable venue, join an existing chapter → accept and complete a task against its actual funds/stock/opportunity → trust/responsibility change with reason → qualifying promotion changes available obligations. No random rank text without the state change. |
| Competition | Two distinct chapters/enterprises compete over a bounded local opportunity → a completed action changes influence or a real market condition → later customer access/contract availability or costs change according to that state. No automatic ownership transfer or cash minting. |
| Incident and law | An eligible voluntary incident creates a dated record; a witness exists only if physically present at the relevant place/time, or an actual action creates evidence. Investigation reads bounded stable evidence and produces a reviewable legal consequence; only discovered evidence is shown to the player. No hidden roll or location alone creates a criminal record. |
| Leaving | An explicit leave action terminates active membership, keeps debts/claims and dated former relationships, and changes later options; legal work and relocation remain available where conditions allow. No automatic erase or forced reset. |
| Family and succession | On death, an eligible successor takes the existing estate and world history; deceased membership ends and legitimate estate obligations persist. Crime, culpability, rank and personal reputation are not automatically inherited. If no eligible adult exists, retain/export the save and show terminal state without promising continuation. |

The interface must distinguish **contractual** rent cash flow from realized payments; next mortgage installment includes accrued interest, not profit. Summaries must not invent costs, witnesses, ownership or venue availability. A limited number of recommendations must select actually available actions and show time, cost, requirements, effects and delayed consequences. History is ordered authoritative events with stable subject IDs and known/discovered provenance; preserve original saved prose when displaying an explicitly marked original-language archive.

## Acceptance and integration gates

Before implementing, agree exact schema/limits, district catalog and canonical mapping with the owners. For each of İstanbul plus one genuinely modeled Ankara/İzmir district, prove deterministic action replay and save/export/import/reload through all six loops. Include: legacy v6/v7 fixtures without initial byte changes; stale-tab conflict/rollback; no duplicate salary, rent, inventory, taxes or case resolution; route/venue/calendar/NPC co-presence; disabled and insufficient-funds paths; discovered-vs-hidden evidence; leave with outstanding obligations; death with and without eligible heir; and expansion remaining opt-in/lazy with one Gold engine instance. Test finite actor/stock bounds, idempotent daily/monthly hooks and phase-2 package budgets without changing the existing frozen assertions. Render TR/EN/PL and keyboard/mobile views from public projections, and verify displayed values against the same preconditions used by the resolver.
